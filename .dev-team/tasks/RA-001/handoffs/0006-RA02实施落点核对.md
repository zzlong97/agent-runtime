| 交付 | 必要模块与当前使用方 |
| --- | --- |
| 受信 Adapter | `capabilities/remote_a2a/capability.py` 及必要内部辅助；Gateway注入受信绑定访问，不扩大普通 Capability SDK。当前 HumanMessage 的文本→稳定UUIDv5 messageId→Send/Get；不发历史/System/State |

| Operation | 复用 `capabilities/operation_ledger.py`：Send=`remote_send:<message_id>`，Cancel=`remote_cancel:<task_id>`；Get只读。先写pending→Send→持久绑定→正常退出标succeeded；异常未知不mark_failed，不将已有succeeded倒退pending |

| 恢复计数 | `chat.py:_recover_persistent_run`、`event_repository.py:claim_recovery` 均有>=3限制；`event_schemas.py`两种恢复事件及`api/schemas/runs.py`有le=3。一起修改；本地三次策略保留，未绑定但可能已受理的open remote Invocation也涵盖豁免；计数真实递增，无紧循环 |
| 取消/超时 | `runtime/coordinator.py`强制取消、`execution.py`超时/强制收尾、Gateway CancelledError、`chat.py:execute_persistent_run/_finalize_persistent_cancellation_locked/_project_stopped_cancellation_locked`等入口均须过远程屏障；不能仅改正常invoke循环 |

## 首个恢复探针及最小验收

1. 先闭合“真实PostgreSQL open Invocation+Task+pending Send Operation→Fake已受理→绑定持久化”的最小路径；在受理后、task_bound写入前设置故障点，不能仅在发HTTP前抛错。
2. 丢弃并重建本地Service/Coordinator/Registry，使用同库同Run恢复，保留Fake远程任务；至少连续接管4次，观察同invocation/messageId/远程Task/context、业务创建计数始终1，Session新Run仍409，Operation未知时pending。
3. 再覆盖绑定后、终态前崩溃，以及绑定已写但Operation尚pending：只Get原Task，不重复Send；Parent终态先写、Run投影前崩溃后仍只有一条公共AIMessage；Get不产生Operation。
4. 定向单测加PostgreSQL探针覆盖：重复初次提交/同ID异内容冲突、取消未确认后重启和后续确认、超时与Cancel并发、删除未知保留所有恢复证据、远程身份变化、错误/日志/内部事件脱敏；保留本地三次恢复和本地取消回归。
5. 预期测试落点：新增remote Invocation/恢复/取消/删除测试，扩充 `tests/capabilities/test_operation_ledger.py/test_recovery.py/test_invocation_gateway.py`、`tests/runtime/test_coordinator.py`、API Run Schema及 `tests/integration/test_checkpoint_recovery_runtime.py` 相邻集成用例。覆盖RA-AC-02后端、04/05、06初次提交、07/08；03、06重复Resume及02页面终验留RA03/集成。

正式文本Interrupt/open Invocation探针仍归RA03开头，随后才完成文本API/UI；RA02不得将input-required当失败或completed，只保留受控内部待接通边界，不提前宣称RA03通过。两探针未通过不得真实联调；不触碰对方仓库、MI/Lease、跨Run上下文或远程数据删除。

## 仅显式 OUT_OF_SCOPE 分支的待裁决交互

- 普通 `TASK_STATE_REJECTED` 无显式码：架构17.3原文“缺少该码的 rejected 一律按远程失败处理”，无需合法拒绝回滚，**不属于争议**。
- 但显式OUT_OF_SCOPE且无Artifact被17.3接纳为合法拒绝；17.4又原文要求“初次SendMessage和每次补参SendMessage都使用 ctx.operation(...)”。
- 既有批准并非只有“业务零副作用”概括：架构15.5原文“验证无公开输出、无 Operation、无 Child Checkpoint→同一事务删除 provisional Task”；同段明确“若已产生 Operation…后拒绝，按 CAPABILITY_EXECUTION_FAILED”。D-056原文亦为“Capability 若已产生公开输出、Operation 或业务 State 后再拒绝，按契约违规失败”。两规则同时应用时，首次远程合法范围拒绝已有传输Operation。
- 实证：`invocation_gateway.py:303～316`检查任意Operation；`persistence.py:1137～1147`事务中再次拒绝任意Operation，且`:120～121`为`task_id REFERENCES capability_tasks ON DELETE RESTRICT`。只跳过Gateway检查仍无法合法删除provisional Task。
- 最小候选影响只在远程显式拒绝的Task/台账生命周期：A保留终态传输台账和关联Task、仅恢复current（改变“删除provisional Task”）；B在确认远程rejected且无业务副作用后原子处理传输台账再回滚Task（改变零Operation及台账保留规则）。二者均非本轮已批准结论，涉及Gateway/TaskService/Repository及对应回滚/重放测试；不增表、不修改普通本地规则，不自行选方案、删台账或放宽约束。
- 总控可先派无争议路径，争议分支保持未实现/未验收，交负责人裁决后再定向更新正文和子任务，不把它当全部RA02重新审批的理由。
