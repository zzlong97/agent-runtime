## 阻塞项 MI01-R01：blob 序列化仍占用 Run 持锁事务预算

- **严重程度/类型：重要，阻塞本批验收；实现偏离已批准短事务边界。**
- **要求：**architecture18.3 明确“序列化、模型、HTTP 和人工等待放在短事务外”；18.4
  要求实际 Saver SQL、管线同步和执行权校验同连接同事务，两个要求须同时满足。
- **实际位置：**`guarded_checkpointer.py:29–34` 在进入 `ownership.guard()`、获得 Run 锁后
  才向框架 `aput()` 让出 cursor。锁定依赖 `langgraph-checkpoint-postgres 3.1.2` 的
  `aio.py:280–294` 随后才调用 `await asyncio.to_thread(self._dump_blobs, ...)`；其
  `base.py:549–566` 执行 `serde.dumps_typed()`。因此 blob 的 CPU/线程排队/序列化等待
  均处于受保护事务内。当前继承方法没有先准备全部数据库写入参数再进入该事务。
- **独立真实复现：**在隔离库 `mi_dev01_20261030_6d2f8b90` 的准确 schema
  `mi01_review_6d2f8b90`，使用本进程自定义序列化器等待 450ms，事务预算 300ms。
  序列化器开始时，由独立连接 `FOR UPDATE NOWAIT` 确认 Run 行锁已被持有；`aput`
  约 498ms 后报 `OperationalError`，失败连接关闭，Checkpoint/blob/write 三表均为零。
  随后同一有效令牌用正常序列化器及新连接写入成功。此结果说明回滚/回收有效，同时
  也实际证伪了“序列化在短事务外”。450ms 是受控慢序列化注入，不声称当前普通样本
  自然需要该耗时，也未改依赖或产品实现。
- **影响：**Checkpoint 状态序列化较慢时，即使数据库健康，仍会占用 Run 行锁、阻塞续租
  或接管，并可能仅因序列化耗尽事务预算而使本次写入失败。原 17 项探针仅覆盖
  SQL/锁/空闲等待，不能排除此路径。
- **建议责任与复核：**由开发在原批准范围内调整 Saver 写入边界，使序列化及写入参数准备
  在短事务外完成，保留写前重新取得 Run 锁/实际时钟/契约/令牌校验，以及真实 SQL 和
  管线同步的原子事务。补真实探针证明慢序列化期间 Run 锁未持有，序列化完成后仍重新拒绝
  缺失/到期/陈旧令牌；保留有效写入、三表回滚及失败连接回收。审核不指定新增架构或平台。
