## MI01-R01 的修复和独立判断

`aput()` 现在先要求执行令牌，再通过 `asyncio.to_thread(_prepare_checkpoint, ...)`
准备全部 blob、Checkpoint JSON、metadata JSON 和 SQL 参数；之后才进入 `_cursor` 的
短事务。`_prepared_json()` 使用驱动 JsonbDumper 先生成实际 JSON 字节，实际 execute
时 Jsonb 的 dumps 回调只返回这些字节，不把惰性 JSON 编码藏到持 Run 锁阶段。

已逐项对照锁定 `langgraph-checkpoint-postgres 3.1.2` 的 `aput/_dump_blobs` 与
`psycopg 3.3.5` 的 JSON dumper：primitive 内联、复杂值 blob、DeltaSnapshot 标记、
new_versions 筛选、metadata 清理、namespace、父 checkpoint 和 SQL 参数顺序一致。
读取仍沿用框架。`aput_writes()` 前置令牌检查；锁定框架自己的 `_dump_writes` 本就在
cursor 外，实际写入继续沿原管线，不另行复制其索引/错误通道语义。

参数准备结束后才在原 `_cursor` 中重新读取上下文令牌，随后重新锁 Run、验证契约、
owner/epoch 和锁后数据库实际时间。原同连接局部 Saver 与管线退出同步仍在 guard
提交之前；没有临时修改共享 conn，没有通用绕过开关。准备异常在进入事务前退出，
日志只记 Run 标识、错误类型与耗时，不记录参数或异常正文。事务预算及领取实现未改。

因此 MI01-R01 的“序列化占用持锁事务”根因已被纠正，同时未放松失权拒绝或原子写入。
本适配明确绑定上述锁定框架表示，未来依赖升级须复核；这不构成本批遗留缺陷。
